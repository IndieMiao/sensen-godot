# C-168: parcel stuck at "The farm preview could not finish loading." (EGL_BAD_SURFACE)

Client problem, made certain by an emulator's software renderer; not an emulator configuration problem.

## Cause

1. "Enter my farm": in one frame AppRouter suspends the map, which asks the map plugin for an opaque Godot surface
   (`setGodotSurfaceOpaque(true)` → `holder.setFormat(RGBX_8888)` on Android's UI thread), and adds the parcel, whose
   `_ready` builds the whole scene. Under `-gpu lavapipe -feature -Vulkan` that frame takes about 19 s.
2. A format change replaces the SurfaceView's Surface without `surfaceDestroyed`; Godot's `GLSurfaceView` only learns
   the new size. A frame in flight then presents to the old Surface: `GFXSTREAM EGL_BAD_SURFACE`,
   `GLThread: eglSwapBuffers failed`. Its `mSurfaceIsBad` clears only once the thread sees no Surface, so Godot draws
   nothing more until the app is backgrounded. Godot's `surfaceDestroyed`/`onPause` do not wait for the render
   thread (checked in the 4.7.2 template's `godot-lib`), so any in-flight frame races the change — also the
   2-frame waits, and going back to the map (`RGBX_8888` → `TRANSLUCENT`).
3. Back from the background Godot draws again, but the 15 s loading limit was wall time from `_ready`: already spent.
4. Retry builds again; `_ready` alone takes ~19 s, so the first `_process` is past 15 s and fails at once.
   On a faster machine (C-101#17) `_ready` stayed under 15 s, which is why background + Retry once worked.

## Fix

- `GodotMapPlugin.applyGodotSurfaceMode`: while Godot's main loop runs, the format change is queued on Godot's render
  thread (`queueOnRenderThread`); between frames it posts `setFormat` to the UI thread and waits for it (≤ 1 s). No
  frame is in flight; the thread then sees the new size and makes its EGL surface on the new Surface. Before the main
  loop starts the format is set directly, as before.
- `dynamic_farm_host`: the first build waits until the plugin reports the opaque surface made (≤ 1.5 s), then two
  drawn frames, so the long build frame never overlaps the change. Android singletons are asked through
  `has_java_method`.
- `dynamic_farm.gd`: the loading limit counts drawn frames only (`LOAD_LIMIT_S` 15, each frame ≤ 0.25 s): the build
  in `_ready`, a lost surface and the background no longer spend it.

## Emulator used (cardigan-ci)

Private AVD, `system-images;android-37.0;google_apis_playstore_ps16k;x86_64`, pixel_6 1080×2400, 4 GB,
`-no-window -no-audio -no-snapshot -gpu lavapipe -feature -Vulkan`, adb `-P 5137`. The package's two Journey URLs
point at a local in-memory server through `10.0.2.2`. With the fix the parcel opens and closes there without
`EGL_BAD_SURFACE`. With 4 GB the guest can kill the app at start after several runs (low-memory killer);
relaunching was enough.

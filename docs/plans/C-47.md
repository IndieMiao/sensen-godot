# C-47 P0CityPlaces / P0WildSites 静态回调表在退出时的崩溃风险

## 结论

- 机制成立，已在本机复现：P0 地图发出的城市读或野外点读还没回来时退出，会和 C-41 一样以 134 崩溃。
  复现用的是真实的 `p0_map`、两个真实模块，以及正式包走的网络路径：没有测试 transport，请求经 P0HttpRequest
  发出，回调就是地图自己的 lambda。
- 但是否崩溃取决于引擎退出时各脚本的拆除顺序。按正式包实际的几种进入方式各跑 3 次，都没有崩溃。只有在一个比地图脚本更早创建、
  又 preload 了这两个模块的脚本存在时，才稳定崩溃。测试套件正好就是这种脚本。所以：**正式包里没有复现到，也不能排除**。
- 手机正式包没有实测，原因见下文“没有验证的部分”。
- 防护（4 行）：P0Runtime 离树时清空两个模块的等待表，与同一处已有的 `WaterShore.finish_all()` 同一个做法。
  加了防护后，同一复现方法不再崩溃。按验收第 2 条，加不加这层防护由 PM 决定。

## 根因（与 C-41 同一个引擎缺陷）

`P0CityPlaces._pending/_failing`、`P0WildSites._pending/_failing` 是脚本静态变量，读还没回来时，里面存着调用方的回调。
`p0_map.gd` 传进去的多是用到 `self` 的 lambda（`open_city_card`、`_process` 里每 0.4 秒一次的野外点读、旅行卡、
`show_place`）。野外点模块还会再套一层自己的 lambda，把调用方的回调捕获进去。

进程退出时，`GDScriptLanguage::finish` 逐个清理脚本。如果 `p0_map.gd` 先被释放
（`--verbose` 打出 `GDScript: N orphaned lambdas becoming invalid at destruction of script 'res://scenes/p0/p0_map.gd'`），
之后再清模块的静态变量，销毁这些 lambda 时就会去锁已释放脚本里的互斥量。macOS 上表现为
`recursive_mutex lock failed: Invalid argument`，退出 134。详细调用栈见 docs/plans/C-41.md（ASan）。

读一旦有结果（回话、失败或 8 秒超时），`accept`/`fail` 就会把记录删掉，所以只有在读还没回来的那几秒里退出才会出事。
地图在城市细节层（缩放 ≥ 9，进地图默认 13.7）时，打开后 0.4 秒内就会发出第一条野外点读，所以这个时间窗口很常见。

## 复现方法与证据

环境：mac-mini，官方 Godot `4.7.2.stable.official.ed1daf0bf`（/opt/homebrew/bin/godot），`--headless --verbose`。
基线 `666b8cdbf88e8e4cd2fce0b4b9b6703cc998e09d`（origin/integration/dynamicfarm，含 C-41）。

复现脚本没有入库，放在交付附件里。做法如下：

- 用一个只 accept、从不回话的本地 TCP 服务（127.0.0.1:18047）充当服务器，并设 `P0_SERVER_URL` 指向它。
- 实例化真实的 `scenes/p0/p0_map.tscn`，让读在 1 秒时发出，3 秒时 `get_tree().quit()`。这时仍在 P0HttpRequest 的 8 秒等待内。
- 用例：wild（地图自己的野外点读）、city（关掉地图 `_process`，只开城市卡）、both（两者都有）、settled（等读超时后再退出）、
  freed（读未回时先释放地图，读超时后再退出）。
- 脚本创建顺序（拆除时最新创建的先清）：
  - held：场景脚本先 preload 两个模块。这个顺序是构造出来的，和测试套件 preload 模块的情形相同。
  - map：地图是第一个加载的 P0 场景。
  - runtime：先建 runtime，再按收到第一份 state 时那样读家乡城市，最后才开地图，与正式包相同。
  - boot：真实入口 p0_boot.tscn，`P0_SCENE=map`。
  - farm：runtime → 读家乡城市 → 农场作为根场景 → `P0Runtime.leave_to_map()`。这是正式包从农场去地图的路径。
  - app：项目主场景 city_select.tscn（`SENSEN_P0=1`）→ p0_boot → 地图。

修复前（基线 666b8cdb）：

| 顺序 / 用例 | 结果 |
| --- | --- |
| held / wild、city、both，各 3 次 | 9 次都退出 134，`recursive_mutex lock failed`；`orphaned lambdas ... p0_map.gd` 分别为 7、1、8 个 |
| held / settled、freed，各 3 次 | 退出 0（读已超时，记录已删） |
| held / wild、city，退出前手动清空 `_pending/_failing`，各 3 次 | 退出 0 |
| map、runtime、boot、farm、app / wild、city，各 3 次（共 30 次） | 都退出 0，没有 `orphaned lambdas`；退出时 `_pending` 里仍留着读 |

加防护后（同一套复现方法，不手动清空）：

| 顺序 / 用例 | 结果 |
| --- | --- |
| held / wild、city、both、settled、freed，各 3 次 | 15 次都退出 0，没有 `orphaned lambdas` |
| map、farm、app / wild、city，各 1 次 | 都退出 0 |

freed 用例说明：游戏进行中地图被释放（换场景），之后读再超时，这种情况不会崩溃，地图脚本仍在。
所以风险只在退出时。

## 测试里的同类情况

我临时在 gdUnit 每个套件结束时打印两个模块的等待表（没有入库），按字母序跑了与这两个模块相关的 43 个套件：

- `test_p0_map_fog` 结束时留下 `gn-5336269` 的 2 个回调，`test_p0_map_travel` 留下 `gn-1850147` 的 1 个；
  `test_p0_travel_flight` 之后有 45 个回调，一直留到后面的套件清掉为止。
- 字母序下，后面的套件会把它们清掉，退出 0。单独跑 `test_p0_map_fog`、`test_p0_map_travel` 也都退出 0，
  没有 `orphaned lambdas`。
- 换一种套件顺序会不会像 C-41 那样崩，没有逐一验证。加防护后，跑完各套件 `after()` 里的 `P0Runtime.free_instance_for_tests()`，
  等待表就会被清空。同样 43 个套件加 `test_p0_session_queue`，共 466 例全过，退出 0。
  45 个回调那一处已经没有了；map_fog、map_travel 留下的记录在下一个套件开始前就清掉了。

## 防护（修法）

- `P0CityPlaces.drop_waiting()`、`P0WildSites.drop_waiting()`：只清 `_pending/_failing`。已经读到的城市和野外点保留，也不通知等待方。
- `P0Runtime._exit_tree()`：在已有的 `WaterShore.finish_all()` 后面，对已加载的这两个模块调用 `drop_waiting()`。
  用 `ResourceLoader.has_cached` 判断是否已加载，退出时不会为此新加载脚本。
  - 退出时，节点先离树，之后才拆脚本（`WaterShore.finish_all()` 依赖的也是这一点）。这些回调因此在地图脚本还在时就被销毁。
    上面加防护后的 15 次 held 运行与此一致。
  - 正常游戏中，runtime 只在切换测试账号时离树（`queue_free` 后重建）。这时它的 session 和 session 下的
    P0HttpRequest 会一起被释放，这些读本来就不会回来了。清掉记录后，新的 runtime 再问同一个城市会重新发读，
    而不是挂在一条已经死掉的读上。
- 新增用例 `test_p0_city_places.gd::test_the_runtime_leaving_drops_the_reads_still_out_and_keeps_what_was_read`。
  去掉 runtime 的改动后，这个用例 4 条断言失败；恢复后通过。
- 没有改 C-41 修过的 P0HomePick 和它的测试，没有改 CI、退出码判定和清理流程。

## 没有验证的部分

- 手机正式包没有实测。
  - 正式签名需要凭据；按规定不碰 ADB 5037 和 USB 真机；/Volumes/ACASIS 上的 AVD 在本会话里不可读（TCC，见 C-41#16）。
  - 从代码看，Android 返回键是 `moveTaskToBack`（app_router.gd `_leave_app`），不会退出；iOS 不会主动退出。
    引擎只有在 Activity 被正常销毁时才会走这段清理，被系统杀进程时不会走。所以手机上能撞上的机会比桌面少，但不能排除。
  - 已核对 Android 正式模板 `android_release.apk` 的 `libgodot_android.so` 里有 `orphaned lambdas becoming invalid at destruction of script`
    这段代码，说明正式模板里也有同一段 lambda 失效逻辑。
- 正式包的几种进入方式为什么不崩：推测是地图脚本在这些顺序下比两个模块拆得晚，但没有引擎源码，没有逐行核实。本机无法访问 GitHub。

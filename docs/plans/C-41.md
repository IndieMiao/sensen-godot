# C-41 Linux 完整 p0 收尾崩溃复发（exit 134）

## 基线是否含 C-24 修复

含。基线 `4e52c4e8f70d85ed8258a5985a09da4deaa9cf4b` 的祖先里有 C-24 的修复提交 `d3122c66675d411881188c7f12cebfa905301713`
（`git merge-base --is-ancestor` 成立），`addons/gdUnit4/bin/GdUnitCmdTool.gd` 的 `_finalize` 已经先判断 runner 是否有效。
这次复发是另一处问题，不是 C-24 的修复丢了。

## 根因（macOS 上已实证）

1. `tests/p0/test_p0_ui_controls.gd` 的 `test_the_home_pick_hides_the_hud_till_it_closes` 用一个不回话的测试 transport
   打开选家流程。`P0HomeFlow._ready` 读城市列表，`P0HomePick._read` 把两个回调存进静态变量
   `P0HomePick._waiting["/p0/home/cities"]`：一个是 `P0HomePick.cities` 里的静态 lambda（它捕获了流程的 lambda），
   一个是 `p0_home_flow.gd` 的 lambda 本身。这条读一直没有回话，这个套件也不清 `_waiting`。
2. 只有 `test_p1_home_pick`、`test_p1_home_change`、`test_p1_guide_test_accounts` 三个套件会调 `P0HomePick.clear()`。
   套件顺序来自 gdUnit 扫目录时 `DirAccess.get_next()` 的顺序，也就是文件系统的目录顺序：macOS 上它们排在
   `test_p0_ui_controls` 后面，记录被清掉；换一种目录顺序，`test_p0_ui_controls` 排在它们后面，这条记录就一直留到进程退出。
3. 退出时 `ScriptServer::finish_languages()` → `GDScriptLanguage::finish()` 逐个脚本 `clear()`。`p0_home_flow.gd`
   先被释放（`--verbose` 打出 `GDScript: 2 orphaned lambdas becoming invalid at destruction of script
   'res://scenes/p0/panels/p0_home_flow.gd'`），之后才清 `p0_home_pick.gd` 的静态变量。这时销毁那两个 lambda，
   `GDScript::UpdatableFuncPtr::~UpdatableFuncPtr()` 会去锁已释放脚本里的 `func_ptrs_to_update_mutex`，属于释放后写。
   这是 Godot 4.7.2 的引擎缺陷，与上游 godotengine/godot#123712 同类（静态或全局存放、比所属脚本活得久的 lambda）。
4. macOS 上，锁一块已释放的互斥量会返回 EINVAL，`std::recursive_mutex` 抛异常后 abort，进程退出 134。
   glibc 上 `pthread_mutex_lock` 直接改写那块已释放的内存，写坏堆块头，等后面某次释放时才报
   `corrupted size vs. prev_size in fastbins` 并 abort。这和 CI 日志里的顺序一致：`Exit code: 0` → `Run dispose test resources`
   → glibc 报错，之后没有 `ObjectDB instances leaked` 警告（崩在 `ObjectDB::cleanup` 之前）。
   是否撞上取决于套件顺序和退出时脚本的释放顺序，所以看起来是随机失败。

Linux 上的对应关系是推断：同一个释放后写在 glibc 下表现为堆损坏，还没有在 Linux 上直接截到调用栈。
Linux 上的对照验证见卡片（倒序运行的 A/B、修复后连续 3 次完整 p0）。

## 证据

环境：mac-mini，官方 Godot `4.7.2.stable.official.ed1daf0bf`；ASan 版是同一 tag（`4.7.2-stable`）自己编译的 macOS editor
（`scons platform=macos arch=arm64 target=editor use_asan=yes debug_symbols=yes vulkan=no metal=no opengl3=no angle=no accesskit=no`）。
套件顺序用 `-a res://tests/p0/<file>.gd` 逐个传入，gdUnit 按传入顺序执行。

| 运行（基线 4e52c4e8，未修） | 结果 |
| --- | --- |
| 默认目录顺序，官方版 / Guard Malloc / ASan | 2242 全过，退出 0 |
| 字母序，ASan | 2241/2242（1 条计时用例在 ASan 下变慢），无 ASan 报告，退出 100 |
| 字母倒序，ASan | 2242 全过，之后 `recursive_mutex lock failed: Invalid argument`，退出 134 |
| 字母倒序，官方版（5 次，其中 3 次在 `_finalize` 加了只读打印、1 次 `--verbose`） | 每次 2242 全过，之后同一报错，退出 134 |
| 字母倒序，ASan + `handle_abort=1` | 调用栈：`Main::cleanup` → `ScriptServer::finish_languages` → `GDScriptLanguage::finish` → `GDScript::clear`（gdscript.cpp:1453，`static_variables.clear()`）→ Dictionary → Array → `GDScriptLambdaCallable` 的捕获 → `GDScriptLambdaSelfCallable::~` → `recursive_mutex::lock` → abort |
| 字母倒序，在 `_finalize` 打印 `P0HomePick._waiting` | `["/p0/home/cities"]`，写入它的是 `test_p0_ui_controls.gd:test_the_home_pick_hides_the_hud_till_it_closes` |

ASan 的阳性对照：临时撤掉 C-24 的 `is_instance_valid` 判断，ASan 版立即报
`heap-use-after-free ... SceneTree::queue_delete`，说明这套工具能抓到这类问题。

## 修法

`test_p0_ui_controls.gd` 的 `after_test` 调 `P0HomePick.clear()`，和另外三个用到选家读的套件一样，测试结束就放掉没回话的读，
不让流程的 lambda 留到退出。没有改用例、清理流程、退出码判定或 CI。

| 运行（修复后） | 结果 |
| --- | --- |
| 字母倒序，官方版 + `--verbose` | 2242 全过，退出 0，没有 `orphaned lambdas` |
| 字母序 + 4 种随机顺序（种子 1–4），官方版 + `--verbose` | 每次 2242 全过，退出 0，没有 `orphaned lambdas` |
| `tools/run_tests.sh --ci-headless res://tests/p0` | 2242 全过，退出 0 |
| `tools/run_tests.sh --ci-headless res://tests/ui_kit` | 347 全过，退出 0 |

## 同类风险（本卡不改）

`P0CityPlaces._pending/_failing`、`P0WildSites._pending/_failing` 也把调用方的 lambda 存进静态变量，等读回来再调。
现有测试都会在 after 里 `clear()`；正式包里如果在一条读还没回来时退出，理论上也会走到同一个引擎缺陷。是否处理由 PM 定。

# C-200 地图 Mapbox 3D 调研：3D 地图、地块自定义模型、开垦地块微缩模型

依据：所有者在 SEN-Q-283 的原话（SEN-C-187#58）：“地图的美化希望做下面的调研 1. 启动mapbox的3D地图 2. 调研是否可以自定义3D区块的模型
3. 如果可以的话,是否可以进行以下优化: a) 选择区块变成3D b) 已经开垦的区块(无论是自己还是别人),以微缩景观(抽象的更加卡通/风格化的微缩模型)来简化的表现每个地块的大致开垦情况
c) 地图上微缩版的模型仅需要基于农场的布局,表现出来主房间, 主要建筑(鸡舍牛棚等) 其他的次要的建筑,以及田块和植被这些不需要在地图层级展现”。
参考图是 Mapbox Standard 的 3D 楼和一辆 3D 车（SEN-C-187 attachment-1777、1778）。地块之间的移动沿用 SEN-C-187 的头像曲线方案，不在本卡范围。

本文只合入这份报告；原型代码留在本地分支 `proto/C-200`，不合入（完整 SHA 见第六节）。

## 结论速览

| 问题 | 结论 | 代价 |
| --- | --- | --- |
| 1 开 3D 地图 | 能。现有 Mapbox 11.29 不用升级、不用新权限，原型已在模拟器上打开 3D 地图。两种开法：现有 Streets 样式上加一层“立体楼”图层（改动最小），或换成 Mapbox Standard 样式（自带 3D 楼、地标、树和光照） | Streets 加立体楼：只改原生地图插件，加一层图层和光照；换 Standard：现有城市配色、标签语言、地块图层顺序都要按 Standard 的方式重做 |

## 一、现状：SDK 版本和接入结构

**版本**

- Android：`com.mapbox.maps:android-ndk27:11.29.0`（`tools/android/overlay/build.gradle`，ndk27 版本是为了 16 KB 对齐）。从 Mapbox 公开 Maven 仓库匿名下载，不用下载 token。
- iOS：Swift Package `mapbox-maps-ios`，`upToNextMajorVersion` 从 11.28.0 起（`tools/ios/setup_ios_g3.sh`）。仓库里没有锁定文件，实际解析到的小版本本卡未核。

**接入方式**（原生地图垫底，Godot 透明叠在上面）

- Android 插件 `GodotMap`（`tools/android/overlay/GodotMapPlugin.kt`，源码编进安装包，不是预编译 AAR）。层序自下而上：Mapbox `MapView`（SurfaceView）→ Godot 渲染面（media overlay，半透明）→ 系统界面。
- 地图不接触摸。所有手势都在 Godot：`modules/dynamic_farm/map/geo_native_camera.gd` 算出相机，每次变化调用 `setCamera(lat, lng, zoom, bearing, pitch)` 推给原生。
  - 倾斜已经支持：双指上下推，0–70°，默认 0°。
  - 朝向固定 0°。Godot 的屏幕↔经纬度换算（`geo_screen`/`screen_geo`）按“北朝上”写的。
- 地块全部在原生层画（`ParcelMapController.kt`）：
  - 地块矢量瓦片（`parcels` 图层，按 `block_id` 选中），只用来点选，不画出来；
  - DataSF 建筑轮廓按“自己绿 / 别人红 / 选中黄”上色；
  - 地址和认领者昵称两层文字；
  - 起步区遮罩。
- 图钉、头像、按钮都是 Godot 控件，按同一相机投影到屏幕（`scenes/dynamic_farm/town_entry.gd` 的 `UiMapDestination` 即锁定组件 LOCK-24）。
- 样式是 Mapbox Streets v12（`Style.MAPBOX_STREETS`）。
  - 城市配色是运行时逐层改颜色（`applyCityStyle`），没有自定义样式 JSON。
  - 标签语言用客户端 `localizeLabels`。
  - 投影锁 Mercator。
  - 没有 Standard、地形、天空、立体楼图层。
- iOS 是早期验证结构：`tools/ios/MapUnderlay.swift` 经本机 UDP 收相机和样式指令，没有地块图层（`docs/qa/dynamic-farm-native-bridge-2026-11-18.md` 已写明）。

**每块地的布局数据**

- 地图本身不带农场布局。
- 布局在服务端农场存档：`server/src/parcels/farm.ts` 的 `buildings[]`，每栋有 `type`、`x`、`y`、`width`、`depth`、`rotation`（0–3，每档 90°），单位是游戏格。
- 每块地的格网到经纬度的换算在数据集的 `farms/<id>.json`（约 3 KB），包括：
  - `source_transform`：UTM 原点和旋转角；
  - `grid.origin_cell`；
  - `game_cell_m`：r8 为 0.8 m。
- 地图上的认领查询 `GET /v1/parcels?bbox=` 只返回编号、归属和昵称，最多 500 条（`BBOX_LIMIT`）。

## 二、问题 1：能否开 3D 地图

能，现有版本就行。有两种开法：

**做法 A：Streets 上加立体楼（原型默认用这个）**

- Streets v12 的 `building` 图层本来就有 `height`/`min_height`/`extrude` 字段，只是现在画成平面。
- 加一个 `fill-extrusion` 图层，按高度拉起来，再配一组 3D 光照（环境光 + 方向光）。
- 现有城市配色、地块上色、标签语言都不用动。
- 原型在模拟器上实拍：旧金山 Alamo Square 一带的楼都立起来了，见第六节截图 A。
- 注意：模拟器上开了光照阴影以后整屏地图发黑，原型默认关阴影（第六节“阴影问题”）。
- 不足：
  - 立体楼只有灰白体块，没有 Standard 的立面、地标模型和树。
  - 现在给“自己 / 别人 / 选中”上色的是 DataSF 平面轮廓，立起来以后颜色压在楼脚，看不清。要改成给立体楼本身上色。DataSF 轮廓没有高度，可以用 Mapbox 楼的高度，或在数据集里补 DataSF 的高度字段。

**做法 B：换成 Mapbox Standard**

- Standard 自带 3D 楼、立面、地标模型、3D 树、时段光照（`lightPreset`：dawn / day / dusk / night）和主题（`theme`：default / faded / monochrome / custom）。
- 可配置的开关和颜色（Android 11.17 起）：`show3dBuildings`、`show3dTrees`、`show3dLandmarks`、`show3dFacades`、`colorBuildings`、`colorBuildingSelect` 等。
- 原型可以用启动参数切到 Standard（第六节截图 B）。
- 代价：
  1. 现有城市配色靠逐层改颜色，Standard 不暴露底图图层，只能改成它的配置项或自定义主题。
  2. Standard 不支持客户端改标签语言：原型第一次切 Standard 时，现有的 `localizeLabels` 直接抛异常，应用闪退。语言要改走 Standard 自己的语言配置。
  3. 自己加的图层要放进 Standard 的 `slot`（bottom / middle / top），否则盖在所有东西上面。
  4. 现有 DataSF 楼底色层照抄 Streets 的 `building` 图层颜色，Standard 下没有这个图层，要另写。
  5. Standard 更重，中端机帧率要真机测。

**倾斜和朝向**

- 倾斜已经有：Godot 相机支持 0–70°，原型把默认值改成 60°。
- 要让玩家转朝向，Godot 的投影换算要加朝向，图钉和头像都依赖它。这一项不是开 3D 的必要条件，可以先不做。

## 三、问题 2：能否在地块位置放自定义 3D 模型

能。用 Mapbox 的 `model` 图层（Android/iOS 11.0 起；先前调研 `docs/superpowers/specs/2026-08-25-3dmap-mapbox-research-appendix.md` 记录了 11.17 起该图层不再是实验接口）。

**模型格式**

- 格式是 glTF 2.0（`.glb` 或 `.gltf`），PBR metallic-roughness 材质。
- 来源三种：
  - 安装包内资源（`asset://`，原型用的就是这个）；
  - `https://` 地址；
  - Mapbox 账号上传的 `mapbox://`。
- 限制（来源：Mapbox 样式规范和上面那份调研）：
  - 单个网格最多 65,536 个顶点（16 位索引）；
  - 不支持模型自带动画：关键帧、骨骼、变形都不行。能做的只有整体或命名节点的旋转、材质颜色和透明度覆盖；
  - 不支持 WebP 贴图。
  - 压缩扩展（Draco/Meshopt）在原生 SDK 上的支持本卡未核，建议先用不压缩的 GLB。

**每个模型能分别控制什么**

数据源是 GeoJSON 点，每个点一个模型。以下属性都可以按点的字段取值（数据驱动）：

- `model-id`：用哪个模型；
- `model-rotation`：朝向；
- `model-scale`：大小；
- `model-translation`：偏移；
- `model-color` 和 `model-color-mix-intensity`：染色。

有两个例外：

- 按缩放级变化的大小，在 GeoJSON 数据源上不支持；
- 按点变化的透明度，在 GeoJSON 数据源上不支持（只能整层一个透明度）。

**数量和性能上限**

- Mapbox 没有公布模型数量上限。
- 有一个 `model-allow-density-reduction`（11.20 起，默认开）：远处、低缩放级时自动减少数量，Standard 的 3D 树就是这样画的。
- 本卡在模拟器上做了数量对比（第六节表格）。模拟器是软件渲染，数字只能看相对变化，不代表手机帧率；真机实测列为后续项。
- 建议的预算（作者默认值，真机测完再定）：
  - 每个微缩件 ≤ 500 个三角形、不用贴图、只用纯色材质（原型占位件整个 84 个三角形）；
  - 同屏 ≤ 200 个件；
  - 缩放级 < 16 时不画。

## 四、问题 3：a、b、c 的做法和代价

### 3a 选中地块变 3D

- 做法 1（原型已做，第六节截图 C、D）：
  - 选中地块时，原生层从点选结果拿到地块中心（瓦片里的 `center`，是 JSON 字符串），把模型放到那里；
  - 同时把这块地自己的楼从立体层去掉。DataSF 轮廓带 `block_id`，按它过滤即可；
  - 点别的地块，模型跟着移过去。
- 做法 2：给选中地块的楼单独拉高、换颜色（`fill-extrusion` 按选中状态取值），不另加模型。
- 要把真实的楼换成微缩模型时，可以用 `clip` 图层把这块地范围内的 Mapbox 模型和标注裁掉。
  - 裁剪只对 model 和 symbol 图层有效（样式规范 `clip-layer-types` 只有这两种），对 `fill-extrusion` 立体楼无效。
  - 做法 A 下用过滤条件把这块地的楼排除（原型就是这样做的）。Standard 的普通楼能不能裁掉本卡未核，地标和树是模型，可以裁。
- 代价小：原生层改动，加一个模型文件，不加网络请求。

### 3b 已开垦地块（自己和别人的）用微缩模型

**怎么按农场布局生成**

- 不为每块地单独建模型，用“零件拼装”：每种主要建筑一个小模型（底板、主屋、鸡舍、牛棚……），每栋建筑在地图上是一个点。
  - `model-id` 取建筑类型；
  - 位置 = 地块格网原点 + 建筑格坐标 × `game_cell_m`，再按地块旋转角换到经纬度；
  - 朝向 = 地块旋转角 + `rotation × 90°`；
  - 大小按地图上看得清的程度统一放大（原型用 1.5 倍）。
- 数据来源建议在服务端算好。在 `GET /v1/parcels?bbox=` 的每条已认领地块里加一个精简字段，例如：
  `"mini":[["cottage",lon,lat,deg],["coop",lon,lat,deg]]`，只含主要建筑。
  - 好处：地图不用为每块地下载 `farms/<id>.json` 和农场存档。
  - 服务端已经有存档和数据集，换算一次即可。
  - 也可以只在存档变化时重算、存下来。
- 开垦程度怎么表现（建议，待所有者定）：
  - 底板颜色或大小按已开垦格数分 3 档；
  - 有主屋才放主屋；
  - 已建鸡舍、牛棚的才放对应零件。
  - 只有“已认领没盖房”的地块，放一块空底板。

**网络流量**

- 模型文件打进安装包：4–6 个零件，每个几十 KB，安装包增加 < 1 MB，运行时 0 请求。改放 OSS 也可以，首次下载后由 Mapbox 缓存。
- 布局数据：每栋约 40 字节，每块地最多 4–5 栋，约 200 字节。
  - 一次视野刷新常见 20–50 块已认领地块，约 4–10 KB；
  - 上限 500 块，约 100 KB。
  - 对比：数据集的建筑轮廓文件 `buildings.geojson` 是 69.5 MB（未压缩大小），C-118 记录一轮进出地图应用共收到 64.3 MB。

**帧率影响**

- 同屏多块地的估计（作者估算，待真机验证）：
  - 按第三节的预算，同屏 ≤ 200 个零件、每个 ≤ 500 个三角形，最多多出约 10 万个三角形。
  - Mapbox 是否把同一模型的多个实例合并绘制本卡未核。按最坏情况每个零件一次绘制，就是最多多 200 次绘制。
  - 对照：做法 A 的 3D 视野里已有上千栋立体楼，所以微缩模型不是主要开销，立体楼本身和阴影才是。
- 见第六节模拟器对比：1 个和 400 个模型在模拟器上只差约 1 帧/秒，但模拟器本身只有 8–9 帧/秒。
- 结论要以真机为准。现有经验：Mapbox 只在相机变化时重画，静止时不耗帧；Godot 层每帧推相机，所以拖动时两边同时出帧。
- 风险点有三个：
  - 立体楼、模型、阴影叠加后中端机拖动的帧率；
  - 阴影：多一遍阴影渲染，而且模拟器上一开阴影整屏变黑（第六节），先关；
  - 模型多时用 `model-allow-density-reduction` 和最小缩放级控制数量。

### 3c 只表现主屋和主要建筑

- 在 3b 的服务端精简字段里按类型过滤即可：主屋（`cottage`，服务端 `HOME_BUILDING`）和养殖建筑（鸡舍 `coop`，以后的牛棚等）。
- 次要建筑、田块、作物、装饰不下发。
- 新增建筑类型时，在服务端的“地图显示类型”名单里登记，客户端放对应零件；没有零件的类型不显示。
- 美术要做的是每类一个低面数、卡通化的微缩件（本卡不做正式美术，原型是 Blender 脚本生成的色块占位）。

### 和 C-187 头像曲线移动的衔接

- 头像和弧线仍然画在 Godot 叠加层，按同一相机投影到屏幕。
  - Godot 的投影已经支持倾斜，起点和终点用 `geo_screen` 换算即可，弧线在屏幕空间画。
  - 微缩模型在 Mapbox 层，两者各管各的，互不影响。
- 要注意三点：
  1. Godot 层拿不到 Mapbox 的深度。头像和弧线永远盖在立体楼和模型上面，不会被楼挡住。地图倾斜时远处的线会显得“浮在楼上”。可以接受的话不用改；不接受的话，起飞时把相机拉平或降低倾角。
  2. 起点和终点的图钉要对准模型的屋顶或底板。图钉锚点要加高度偏移，或者直接指向底板中心。
  3. 先不开放转朝向（见第二节），否则 Godot 的投影要一起改。
- 头像不建议改用 Mapbox 模型：model 图层不支持骨骼动画，现有头像的走路、跳跃动画做不了。

## 五、计费、账号和 token 的影响

- Mapbox 移动端 SDK 按月活计费（Maps SDKs for Mobile MAU）。2026-11-27 抓取的官网价格页：
  - 每月 25,000 月活以内免费；
  - 25,001–125,000 每千个 $4.00；
  - 往上递减。
- 同一个用户一个月内不管看多少次地图、拖多少瓦片，都只算 1 个月活。Android 定价说明写明：月活费用覆盖 SDK 里所有矢量瓦片和栅格瓦片请求。
- 3D 楼、Standard 样式、model 图层、光照都属于 SDK 的渲染功能，不另计费。模型从安装包读不产生 Mapbox 请求。只有改用 `mapbox://` 上传模型或自定义 Mapbox Studio 样式，才会用到账号上的上传和样式功能，本方案不需要。
- 本方案不需要新 token、新权限范围或付费档。
  - 现有公开 token（`pk.`，经 `CARDIGAN_MAPBOX_PUBLIC_FILE` 打进包）就够；
  - 下载 SDK 用的是公开 Maven 仓库，不用下载 token。
- 是否超出现有用量档：本方案不改变月活口径，用量只随玩家数变化。现有账号的实际月活和档位本卡没看（不登录账号后台），所以无法说现在离 25,000 还有多远。
- 本卡没有花钱、没有开账号、没有改或新建 token、没有升级付费档，没有需要人处理的前置操作。

## 七、锁定组件和需要所有者复议的点

**会碰到的锁定组件**

- LOCK-24（P0 复用旧版美术与手感，含“地图交互”和动态农场地图圆钉）：
  - 立体楼和微缩模型都在 Mapbox 层，不改圆钉本身（结构、尺寸、选中样式都不动）。原型也没改圆钉。
  - 默认倾斜、3D 楼会改变地图的观感和手感。现在默认 0°，原型开图就是 60°。这属于“地图交互 / 手感”，正式改要所有者复议。
    不复议的做法是：默认仍然平视，玩家双指上推才看到 3D。
  - 圆钉要指向微缩模型时（第四节衔接第 2 点），锚点要加高度偏移。
    C-187 提的圆钉四项改动（含锚点）所有者没有通过，等本卡结论再定（C-187#62）。锚点偏移应和那四项一起问，不单独改。
- LOCK-08（不做自动跳转）：选中变微缩、显示别人的微缩模型都不移动镜头，不碰。
- 其他锁定项不涉及。

**需要所有者定的点**

1. 底图走哪条路：Streets 加立体楼（改动小、楼是灰白体块），还是换 Standard（更接近参考图，但城市配色和标签语言要重做）。
2. 打开地图默认平视还是倾斜（LOCK-24 复议）。
3. 开垦程度怎么表现：例如底板按开垦格数分 3 档，有主屋才放主屋，有鸡舍、牛棚才放对应零件。
4. 头像和弧线不会被立体楼挡住，是否可以接受（第四节衔接第 1 点）。
5. 微缩件的美术风格和大小：地图上放大多少倍、是否带底板。
6. 立体楼的阴影：模拟器上会出问题，真机测完再定开不开。

## 八、推荐方案和后续拆卡

**推荐**

- 第一步用做法 A（Streets 加立体楼，楼体用 DataSF 轮廓）。
  - 这样可以直接给立体楼按“自己 / 别人 / 选中”上色，3a 选中变微缩也是这条路上做的。
  - 现有城市配色、标签语言、点选都不用动。
- 阴影先关。默认平视，等所有者复议。
- Standard 等所有者看过参考效果再决定，单独开卡。

**拆卡**（供 PM 排期，不在本卡做）

1. 客户端 3D 底图：
   - DataSF 立体楼补高度（数据集加高度字段，或取 Mapbox 楼高），按归属上色；
   - 光照；
   - 3a 选中变微缩；
   - 默认倾斜按所有者复议结果。
2. 服务端：`GET /v1/parcels?bbox=` 加主要建筑精简字段（3b、3c），带“地图显示类型”名单。
3. 美术：4–6 个低面数微缩件（底板、主屋、鸡舍、牛棚等），按第三节的预算。

## 九、风险和未核

- 真机没有测：帧率、阴影合成、内存都只有模拟器数据。
- iOS 没有做：iOS 现有的地图桥没有地块图层，3D 和模型要在 `MapUnderlay.swift` 另做一遍。SDK 能力两端一致。
- Standard 样式未做完整迁移：城市配色、标签语言、地块图层的 slot 都只做了“能跑起来”的程度（原型里 Standard 下的地块上色层没有逐项核对）。
- 立体楼高度：做法 A 用 Mapbox 的楼高；DataSF 轮廓没有高度，原型统一按 9 m 拉高。要和真实楼高一致，需要在数据集里补 DataSF 的高度字段。
- 头像（C-187/C-188）永远画在 3D 楼和模型上面，不会被遮挡（第四节）。
- 现有账号的月活和档位没有看（不登录账号后台）。

# C-50 p0：收件通知用例偶发失败、用例数 2238/2242、失败时退出码

起因：C-41#17（H-41，Linux 官方 Godot 4.7.2.stable.official.ed1daf0bf，7ecf2312）run1 报
`2238 test cases | 0 errors | 1 failures`，失败用例是 test_p0_inbox_notice.gd:36，回帖记的退出码是 0。

以下“实测”都是 macOS（mac-mini，官方 Godot 4.7.2.stable.official.ed1daf0bf，基线
cbfd6cdeb8b13a4491bdb822a1d1e358936c82ba）上的结果；macOS 不算 Linux 通过，Linux 结果见卡上。

## 1. 失败时的退出码

实测（基线，用故意失败的探针：在该用例 `inbox_notice_when_clear` 之后加 `OS.delay_msec(150)`）：

| 怎么跑 | 退出码 |
| --- | --- |
| Godot 直接跑 GdUnitCmdTool（与脚本同参数） | 100 |
| `tools/run_tests.sh --ci-headless <suite>` | 100 |
| `nice -n 10 tools/run_tests.sh --ci-headless <suite>` | 100 |
| `tools/ci/timed.sh p0 tools/run_tests.sh --ci-headless <suite>`（CI 的写法） | 100，并打印 `p0: …s (exit 100)` |
| `nice -n 10 tools/run_tests.sh … \| tee x.log; echo $?`（无 pipefail） | **0**（`PIPESTATUS[0]` 为 100） |
| 完整 p0 `tools/run_tests.sh --ci-headless res://tests/p0` | 100，`2238 test cases \| 0 errors \| 1 failures` |

- gdUnit CI 运行器有失败时 `quit(100)`（GdUnitTestCIRunner.report_exit_code）。脚本 `set -eo pipefail`，
  Godot 非 0 时管道即非 0，脚本以 Godot 的 100 退出；即使 Godot 返回 0，脚本还要求汇总行是
  `0 errors | 0 failures`，否则 exit 1。两道判断都在。
- CI test 步骤是 `tools/ci/timed.sh p0 tools/run_tests.sh --ci-headless res://tests/p0`，timed.sh `set -eu`
  并在 EXIT trap 里保留状态；GitHub 默认 `bash -e {0}`。所以 CI 不会把失败当成通过。
- 推测（未实测，日志在张良的控制主机上）：C-41#17 记的 exit=0 很可能是把输出接到 `tee` 后取的 `$?`，
  取到的是 tee 的状态。上表最后一行能复现这个现象。

固化：tools/ci/test-autoload-gate.sh（CI build 步骤每次都跑）新增对照：一个先失败、后通过的两例套件，
要求 run_tests.sh 以 100 退出且汇总为 3 例 1 失败。去掉本卡的 `-c` 时该对照失败（实测：2 例，脚本报错退出）。

## 2. test_the_card_hangs_under_the_bell_for_two_seconds 偶发失败

根因（实测）：通知卡的 2 s 计时在 P0Ui._process 里扣减，引擎每帧也在调 _process。用例在显示后等两帧，
再手动 `_process(1.9)`，期望还剩 0.1 s。两帧的真实 delta（含显示前同一帧里 set_view、建卡、读图标的耗时）
一旦 ≥ 0.1 s，卡在断言前就已收起。负载高的 Linux（`nice -n 10`、2242 例连跑）上偶尔出现。
在显示后加 `OS.delay_msec(150)` 即可稳定复现，报错与 C-41#17 相同（must not be empty）。

修法：与 test_p0_first_catch 等套件相同，`ui.set_process(false)` 后手动步进；两帧后先 `_process(0.0)`
做每帧摆位，再按原值 `_process(1.9)` / `_process(0.2)` 断言。断言值未改。修后在显示后加
`OS.delay_msec(1500)` 也通过。

同文件和 kitchen_flow、guide_feedback 里其它看通知的断言只在显示后一两帧内检查，要真实耗时超过 2 s 才会
受影响，本卡未改。

## 3. 2238 与 2242

根因（实测）：gdUnit 的 CI 运行器默认对每个套件 fail fast（GdUnitTestCIRunner._ready 里
`_executor.fail_fast(true)`）：套件里一例失败，其后的用例不跑也不计数。test_p0_inbox_notice 共 5 例，失败的
是第一例，其余 4 例被跳过，所以 2242 − 4 = 2238。基线上加探针跑完整 p0，实测正是 2238、1 失败、退出 100。

判断：用例数变化本身是失败的连带结果；但跳过同套件后续用例会把其它失败藏起来，属于缺陷。修法是
`tools/run_tests.sh --ci-headless` 给 gdUnit 加 `-c`（--continue），有失败时也跑完并计入全部用例。
未删除或跳过任何用例，退出码判断未放宽。

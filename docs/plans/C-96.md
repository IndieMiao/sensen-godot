## 设计取舍

1. **邀请账号就是普通的邮箱加密码账号**，由工具直接写库。
   - 客户端可以直接用现有登录面板的“邮箱 + 密码”登录（`/v1/auth/email/login`），C-98 不用新做登录方式。
   - 写库时 `email_verified=true`，身份行记 `sign_in_provider='invite:<批次>'`，用来按批次列出、重置或停用，同时和自助注册的账号区分开。
   - 邮箱放在运营方自己的域名下，只当登录名用。
2. **“有限邀请”必须关掉自助注册**，否则拿到安装包的人照样能注册账号。为此新增开关 `ACCOUNT_SIGNUP`。
   - 设成 `closed` 时：邮箱注册返回 403 `SIGNUP_CLOSED`；Apple、Google 首次登录不建号，同样返回 403；已有账号照常登录。
   - 不设或设成 `open` 时，行为和原来一样。所以开发服、内网测试服和现有测试都不受影响。
   - 设成其它值时，进程拒绝启动，免得拼错后悄悄开放注册。
   - 正式 compose 还把 Google、Apple 登录整个关掉，QA 固定验证码也关掉。
3. **正式开关写死在 compose 的 `environment` 里**：`ACCOUNT_SIGNUP=closed`、`GUEST_WRITES=0`、`DYNAMIC_FARM_RESELECT=0` 等。
   - compose 的 `environment` 优先于 `.env`。
   - `ops.sh check` 发现 `.env` 里写了这些项就拒绝，免得有人以为在 `.env` 里能改。
   - 有自动测试核对 compose、模板和脚本三处一致。
4. **密码不落在不受控的地方**：
   - 工具只把密码写到两种地方：一是新建的 0600 文件，而且不能在 Git 工作区里；二是被重定向的标准输出。
   - 经 `ops.sh` 运行时，标准输出是终端就拒绝，所以 CSV 只会落在操作员 ssh 一侧的受控目录。
   - 先占住输出文件再写库：文件建不出来，一个账号也不建。
5. **建库**：`ops.sh init-db` 用即将运行的那个镜像里的 `schema.sql` 建表，所以建出来的表和这一版的代码一定对得上。`schema.sql` 可以重复执行，app 启动时也会再执行一遍。
6. **备份要证明能恢复**：每份备份都在同一个数据库实例的临时库里真恢复一遍，再从恢复出来的库算行数和指纹（账号、玩家、认领的条数，以及账号和地块存档的 md5），写进 `.counts`。恢复时必须和 `.counts` 完全一致，app 才会启动。
7. **回滚分两档**：
   - 只换镜像：表结构只加不改，旧版能照常读写。
   - 连数据一起回到部署前自动备份的那份。
8. **入口路径**建议用 `/dynamicfarm/v1`。app 只在主机回环地址发布端口，网段固定，这样 `TRUSTED_PROXIES` 能写成一个确定的值。

## 隔离演练结果

时间：2026-11-24。环境：本机 PostgreSQL 16.15，只听 unix 套接字，作为临时库。源码是本卡交付的提交。日志里没有密码；临时目录和密钥在演练结束时已经删掉。

**空库起服务**：

- 空库 0 张表，`ops.sh deploy` 之后是 14 张表。
- 服务日志：`guest_writes=false parcel_reselect=false signup=closed`。
- 只读冒烟全部通过：
  - 健康检查报出的提交号正确；
  - 自助注册返回 403 `SIGNUP_CLOSED`；
  - 游客能读；
  - 游客认领和存档都返回 401 `LOGIN_REQUIRED`。

**邀请账号**：

- `ops.sh invites create --count 3` 的输出重定向到文件，文件是 0600。
- 标准输出是终端时，在连库之前就被拒绝，没有多建账号。
- 两个邀请账号都完成了这一串操作：登录、认领、首次进入（领到赠品）、存档（放房、开垦、播种）、读回。
- 两个账号的“放弃并重选”都返回 403 `RESELECT_DISABLED`。

**备份 → 删库 → 恢复**：

- 备份：账号 3、认领 2，指纹记进 `.counts`；age 加密后删掉了明文。
- 删库：`DROP DATABASE`。
- 恢复：`ops.sh restore … --confirm-drop` 之后，行数和指纹与备份时一致；两个账号重新登录，读回的地块存档与备份前**逐字节相同**；解密出的临时文件已删。

**回滚（实际走了两次）**：

- 部署“下一版”：模拟迁移，给 `parcel_claims` 加一列。部署前自动备份了一份。
- `ops.sh rollback`：回到当前版。新加的列留着，存档不变。
- 再部署下一版，然后 `ops.sh rollback <当前版> --restore <部署前备份>`：库回到部署下一版之前，新列没了，存档不变。

**资源**（参考值）：

- app 进程（tsx 加 node）常驻约 250 MB；
- PostgreSQL 约 90 MB；
- 库 8.4 MB；
- 每份加密备份约 36 KB。

**演练没有覆盖的**（第一次在主机上执行时要看）：

- 真实的 `docker build` / `save` / `load`；
- compose 解析；
- 入口代理和 `TRUSTED_PROXIES` 取到的来源地址。

演练里 docker 换成了替身：替身从 `compose.yml` 读 app 的写死环境变量，按 compose 的规则覆盖 `.env`。

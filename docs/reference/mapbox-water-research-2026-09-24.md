## 附录：真实水域定位调研（本期不采用）

以下保留选型前的资料与抽样。关于真实水域的筛选和接入建议仅供后续研究，本期已选系统鱼塘，不执行这些接入步骤。

| Mapbox Streets v8 数据层 | 官方定义与可用性 | 建议用途 |
| --- | --- | --- |
| `poi_label` | `class` 包括 `park_like`、`sport_and_leisure` 等宽类别；这些类别本身不代表有水或可钓鱼 | 有明确钓鱼语义并通过水域核对的点可成为候选；公园、码头、游泳设施不能整类直接转换 |
| `natural_label` | `water` 对应湖泊、池塘；另有 `reservoir`、`river`、`canal`、`stream` 等；标签包含点和线等几何 | 优先发现有名湖塘和河段，取名称与水域类别；不是完整岸线，也不是现实经营信息 |
| `water` | 包含海洋、河湖、池塘、水库、喷泉等；按瓦片合并，没有可区分具体水体的 `class/type` | 辅助判断附近是否有水；不能用它直接分辨湖塘、喷泉或海洋，不能按每个面创建入口 |
| `waterway` | 线状 `river/canal/stream`；也包含 `stream_intermittent/drain/ditch` | 河段候选；排除排水渠、沟渠和间歇溪流等默认不合适类别 |

官方说明还指出，合并后的要素 ID 可能为 0，或取其中一个输入 ID。水体会随缩放过滤、简化、跨瓦片切分。因此，不能把 `water` 的 feature ID、局部面中心、屏幕中心或当前 zoom 当作永久入口身份。

原真实水域方案评估过的筛选过程：

1. 发现湖塘、河段候选，保留来源及原始语义。现有 OSM 农场地理模块可复用请求与部分解析，但它会将湿地等合并为水域，不能直接用其粗分类判断“可作为鱼塘”。
2. 使用可持久维护的水体资料建立游戏目录：首版可基于现有 OSM 接入或人工核对的自有地点配置。Mapbox 用于底图、运行时发现和显示；不把地图瓦片重组为游戏的永久水体主键。
3. 小湖塘默认一个主入口，大湖或长河只在有明确岸段区分时增加入口。用水体关联和空间距离去重，防止同一处水域同时通过 POI、标签、面、线生成四个点。
4. 已有 POI 原坐标保持不变；自建岸边入口有自己独立的经纬度。两个对象可以关联，但不能为避让图标把真实 POI 搬到岸边。
5. 泛化标签不足以排除喷泉、泳池、工业水池时，需要进一步资料或人工核对；未知状态不自动变成可用鱼塘。

原方案曾考虑以真实湖河名对应缩比例小场景。用户指出大水域与小鱼塘的空间预期不一致，因此本期排除该映射，不使用真实水域名称或轮廓承载系统鱼塘。

### Search Box 是否适合作为主来源

当前官方 Search Box 文档列出的支持地域为美国、加拿大和欧洲，未列中国大陆；其返回数据默认仅供临时使用，持久存储位置需要联系 Mapbox。因此不建议把 Search Box 作为同时覆盖洛杉矶、上海并永久保存入口的基础。它的请求计费也与现有 Maps SDK 瓦片读取不同。

Geocoding v6 已不再提供 POI，不能通过它的永久 geocoding 参数解决上述 POI 目录问题。这里的限制针对对应 API，不能直接套用为所有地图瓦片的存储条款；正式使用 Mapbox 派生持久数据时应核对实际产品授权。默认方案采用可维护的独立地点目录。

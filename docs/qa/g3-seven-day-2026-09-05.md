## Release Boundary

SGODOT-39 still owns branch/CI integration, deployment, compatibility and rollback review. No production deployment or save migration was performed for the evidence above.

- The earlier SGODOT-41 change requires an explicit domain **1 to 2** migration; the state schema remains 1. Startup DDL does not perform that migration automatically.
- G3 decorations and week summaries use compatible optional state fields, but the new authoritative decoration content changes `content_version`. Existing saves with another content version remain blocked by the compatibility gate.
- The existing domain migration tool only accepts the matching release content. It rejects content mismatches and therefore is **not, by itself, a content-version upgrade plan for existing production farms**. SGODOT-39 must resolve that release boundary explicitly; silently replacing content checksums is not an accepted migration.
- Use the same release content for service and migration inspection, stop old writers, review a backup and dry-run, and retain the documented recovery path. None of these production steps is established by a test against `sensen_farm_g3_test`.

See [server migration and content-version instructions](../../server/README.md) for the exact command, compatibility guard and rollback limits.

## 怎样追一条记录

例如在 q 台账查 `q(119)`，先读原话和限定条件，再按来源栏进入 210 的对应评论。审批索引主表第 4 条可用来核对该次发言的时间、署名判断及评论 ID。评论里内嵌的图与「按上传时间推断关联」的图须分开看；两者都不能单独证明用户批准了图上的每个细节。

- q 台账保持原来的 326 行及状态，不把「待批」「作废」「见原卡」「评论未录原话」补成批准。早期记录还涉及 [199](https://plane.sensenjoy.cn/zili/browse/SGODOT-199/) 和 [200](https://plane.sensenjoy.cn/zili/browse/SGODOT-200/)；它们不在这次导出里。`v4q` 是另一组编号，不与 `q` 混排。
- 批准索引的主表是 **491 条发言**，包括提问；另有转述、代写和非回复的附表。保留原文的时间精度（含约时）、飞书位置、Plane 评论 ID 和原日志行号。终端转记不是飞书原话；消息缺失就保留缺口。`status 第 N 行` 指向导出中的 PM 流水，`log.md 第 N 行` 指向原审批日志；后者未随源包导出。不要用当前仓库的行号代替。
- `〔私有路径〕`、`〔机器名〕`、`〔地址〕` 等表示原文在该处脱敏，并非发言者所用字词。需核对这一段时，用来源栏找受控原件；仓库不保存可还原的对照表。发版流程只保留凭据用途和逻辑存放位置。

### 复核原件

拿到 C-8#6 所指的只读导出后，进入相应的 `plane-SGODOT-编号/files` 目录，执行 `shasum -a 256 -c SHA256SUMS`；结果校验的是源文件，不能拿它校验 WebP。例：要回查 302 第 451 条评论，先找 `302#451` 的评论 UUID，再在该卡附件索引查序号和下载状态。汇总表中没有散列的三项不能补记为核验通过。

# 多人下矿的当前边界与建议

日期：2026-09-15。用户询问当前战斗的数据处理与未来多人可能性。本文是架构说明和建议，未实现多人模式。

## 当前实现

当前支持多个账号各自在自己的矿井游玩，不支持多人进入同一矿井、看到实时队友并共同打同一只怪物。

| 数据 | 当前处理位置与方式 |
| --- | --- |
| 移动、障碍、朝向、怪物 AI、蓄力、冲撞、命中扇形、击退 | Godot 客户端逐帧模拟；位置与 AI 阶段不上传服务端保存 |
| 命中结算请求 | HTTP `mine_combat` 上报轮次、楼层、战斗序号、命中怪物 ID、伤害来源 ID |
| 伤害、装备、防御、攻击间隔、受击无敌、怪物剩余生命、击败、掉落 | 服务端 TypeScript reducer 按共享配置验证并结算 |
| 存档 | PostgreSQL 的个人农场 `state` 内保存人物、背包与矿井；同农场行锁、版本号及请求幂等避免重复扣血或发奖 |
| 结果返回 | 每条请求回传完整状态；R3 客户端预测生命反馈并串行异步提交，确认后校正；积压超限暂停，断线复用原请求恢复 |

因此当前是“客户端模拟动作、服务端结算并保存结果”。不是锁步帧同步，也不是服务器权威实时状态同步。
服务端不会检查两个人是否真正在同一个房间或某次挥剑的实际位置，所以不能将当前命中上报协议直接当成多人公平性保证。
同时登录同一账号也不是合作：当前楼层、全局攻击时间、人物 HP 和战斗序号仍只有一份，会互相争用。

生命归零时将该个人存档的矿井楼层设为 0，角色保留 1 点生命；库存、金币、已破岩石与怪物剩余生命保留。R3 在确认救援后自动返回农场人物页，可直接休整。
这是当前的出局/救援方式。再次进入重建角色与怪物场景位置，但不会复活该轮已击败怪物。

## 建议方案

优先做两人合作的服务器权威矿井房间。可采用 Godot 无界面实例作为战斗进程，复用现有网格、移动与战斗配置；
现有 TypeScript 服务继续负责账户、物品和奖励事务。具体技术需先用两台客户端验证同步与延迟，不在本轮混入网络架构改造。

1. 矿井从个人 `farm.state.mine` 拆成独立 `expedition_id` 房间，保存成员、楼层、地图种子、岩石和怪物，个人生命和装备仍按玩家区分。
2. 客户端通过实时连接发送移动方向与攻击意图；房间服务器以固定逻辑步长运行移动、AI、命中与伤害，并广播增量快照。可先以 20 Hz 逻辑、10-20 Hz 快照作为试验参数。
3. 在现有生命反馈预测基础上增加动作预测与服务器校正，其他玩家与怪物使用插值；实时房间快照承载动作结果，个人农场保存仍用于持久化。
4. 活跃位置与 AI 在房间内存中运行，周期性保存可恢复检查点；掉落、消耗与关键进度用事件序号和数据库事务可靠结算，奖励由幂等事件记录避免断线重连重复领取。
5. 房间控制人数和加入权限，怪物仇恨可在成员间切换，同一怪物生命只有一份。参与者不共用攻击冷却或人物生命字段。

首个两人样板建议：统一楼层、共同清矿清怪、按参与者分别发放固定掉落；成员倒下可由队友救起，
全员倒下再统一回农场。队友打开背包时房间继续运行；掉线保留短暂重连窗口，离队不暂停其他成员。
电梯解锁归属、加入时机、掉落规则与救援规则需要在实现前明确；上述规则是建议，不是已发布行为。

验收应覆盖两端同时攻击、抢同一岩石、不同延迟、断线重进、客户端篡改、奖励只发一次、全员离线恢复。
既有物品、装备、伤害公式、角色模型、导航和幂等保存可以复用；房间、实时协议、权威 AI/命中和多人恢复需要新建。

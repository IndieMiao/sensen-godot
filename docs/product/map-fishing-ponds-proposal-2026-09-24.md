# 系统鱼塘：固定地图入口与三种小场景方案

日期：2026-09-24。用户已选定本期只做系统鱼塘，并随后授权实施。现已完成本地实现与隔离验证，见[实现说明](system-fishing-ponds-2026-09-24.md)和[QA 记录](../qa/system-fishing-ponds-2026-09-24.md)；公共发布及真机验收尚未执行。本文保留设计依据，参数以实现说明为准；Mapbox 调研保留在附录。

本期由系统建立独立游戏鱼塘，地图入口、名称、场景预览和进入后的空间共同引用一个固定地点。用户选择这一范围的原因是：大湖、大河对应仅 1–2 屏的小池塘，会产生明显的空间预期落差。系统鱼塘从入口起就表达小型场所，便于控制地图与场景的一致性。

## 本期范围

- 地图采用现有 POI 风格展示系统鱼塘，详情卡提供“进入鱼塘”。
- 位置由固定种子生成并保存，所有玩家共用同一目录。
- 每个入口首次从三种小型鱼塘中分配一个模板，之后固定；装饰变化同样固定。
- 进入后的主要活动范围为约 1–2 个默认手机视野，复用现有角色、自由镜头和沿岸钓鱼。
- 真实湖河入口、Mapbox 水域类型转换和真实水体轮廓重建留在本期之外；系统入口不依赖原生 POI 查询。

“系统生成”描述地点的来源。产品中使用自然的游戏名称和“鱼塘”类别即可，不向玩家展示种子、网格或生成版本。

## 地图与场景的一致性

地图上的系统鱼塘是独立游戏 POI，不覆盖真实湖河名称，不把底图的大水面变成鱼塘入口，也不在底图伪画一片地理水域。

每个地点保存名称、位置、模板和场景版本。地图鱼塘图标可以按三种轮廓区分；详情卡缩略图由对应场景模板生成，进入后使用同一个模板。缩略图若表现该入口的装饰细节，则采用相同装饰种子，避免预览一座圆池而进入另一座长池。

流程为：**地图鱼塘图标 → 白色轻量详情卡 → 青柠色“进入鱼塘” → 沿岸钓鱼 → 返回原地图位置**。

增加“钓鱼”筛选，图标按保存的经纬度直接投影。拥挤时减少标签或按缩放隐藏低优先级点，不移动锚点。图标沿用现有 POI 尺度，有效触区至少 44 逻辑像素；街区尺度显示完整入口，城市尺度显示少量代表点，更远尺度隐藏。

玩家通过游戏地图即可进入。角色使用原有外观、鱼竿和个人库存；未装备鱼竿可以先参观，发起钓鱼时使用现有装备提示。退出恢复地图中心、缩放、朝向、筛选和选中项。

## 位置如何生成并保持固定

建议在洛杉矶、上海各配置少量允许生成的区域及排除区，作为第一版可控边界。可先人工核对底图，选择适合表达小型游戏场所的绿地或开敞区域，避开大湖、海面、主要道路和明显建筑。这里核对的是入口的摆放环境，不要求当地真的存在水塘，也不寻找真实水域锚点。

这组区域属于游戏内容配置，无需在玩家拖图或进场时请求 Mapbox Search Box、OSM 或水域检索服务。后续自动化选址可以单独扩展，不作为本期完整钓鱼闭环的前置。

固定生成建议：

1. 使用米制世界网格索引候选，先试约 1 km 网格、每格最多一个入口、点间距约 600 m；这些值须根据实际地图密度调整。
2. 固定世界种子、网格 ID、允许区域版本和生成版本；同时核对相邻网格，确保结果不取决于玩家浏览顺序或首先进入的账号。
3. 创建时保存 `pond_id`、城市归属、经纬度、名称、模板 ID、装饰种子、布局版本、生成版本和启用状态。以唯一键和原子写入处理同时生成，得到所有玩家共用的地点目录。
4. 模板首次从三种中近似等概率分配后保存。再次进入、跨缩放、自动切城、换设备和服务器重启都沿用原结果。
5. 已建立地点不随算法升级自动重排。城市归属由地点配置决定，不能因地图标题切换而产生第二套入口；需要停用的点有显式状态。
6. 服务端按视口或网格返回已登记地点，客户端缓存并显示；外部地图标签、瓦片 ID 和手机随机数不作为地点权威来源。

地点、场景和装饰的固定随机与每竿鱼获的随机分别处理；场景种子不参与客户端奖励决策。

## 1–2 屏的小场景

按当前角色比例和默认手机镜头衡量主要活动范围，不能通过缩小角色来达成面积目标。

- 灰盒起点建议约 **12 × 16 m** 活动范围，外围装饰约 **16 × 20 m**；最终以原生画面和三种屏幕比例实测调整，米数尚未验收。
- 首屏能看到角色、水面和可钓岸线；至多一次短距离拖动即可查看主要区域。
- 出生点到最近可钓岸线的步行目标约 3–5 秒，岸带连通，可从多个位置钓鱼。
- 复用农场 `ScenePan`：自由拖动、衰减惯性、新触摸停止、焦点缩放、后台取消和离屏头像回位。
- 点击水面选择落点，角色走到可达岸边后由玩家主动抛竿；近岸植被保持低矮，浮漂和收线反馈清晰可见。

## 三种鱼塘表现

以下三种形状作为当前美术与灰盒建议，尚未完成视觉验收。它们都表达可在 1–2 屏内探索的小型池塘。

| 模板 | 水面轮廓 | 主要视觉与空间差异 |
| --- | --- | --- |
| 月牙池 | 弯月形，一侧浅凹湾 | 碎石浅滩、少量睡莲、弧形草岸；开敞且主体易辨认 |
| 葫芦池 | 大小两个水湾通过短窄水颈连接 | 一侧芦苇、一侧清水石岸；绕过陆地鼻角可看到另一水湾 |
| 曲湾池 | 狭长 S 形，宽窄变化，两端收口 | 弯曲岸线、碎石与草岸交替，轻微流向纹理，始终呈现一座完整小池塘 |

每个地点的形状与装饰固定。同模板可在预先校验的范围内变化朝向、石头组合、植物疏密、水色与花草；首版不在运行时任意扭曲岸线。

三种模板共用现有鱼种、价格、难度和一份公共鱼塘掉落配置，形状不直接决定收益。地图中的系统鱼塘作为新增地点，不随机改造用户已有农场池塘。

水面、材质和植被共享，植被使用批量实例，复用已有静态/按需岸边反射；仅装载当前场景所需资源。退出释放导航、反射与联机对象，性能以移动端实测确定。

| 模块 | 本期处理 |

| 服务端地点与实时空间 | 新增固定地点目录和 `pond` 空间，按登记地点提供布局及权威钓鱼参数 |
| 钓鱼、背包和恢复 | 沿用装备检查、服务端结算、个人鱼获、满包溢出、取消与未确认命令恢复 |

异形池不能只修改水面贴图。当前水域判断主要支持椭圆与线段胶囊，需要扩展凹轮廓判断：人不能穿水，抛竿不能越过中间陆地后落入另一水湾。客户端与服务端使用相同模板版本及校验值，着色器的浅滩、深度和鱼影也依据对应岸线。

实时网关当前只接受 `street/farm/mine`，且旧 `street` 请求会转到农场，因此需要显式新增鱼塘空间。格里菲斯的本地游览切场可以复用，但它本身不提供鱼获结算。服务器根据登记的 `pond_id` 选择场景、导航和鱼群配置，不接受客户端任意提交形状或权重。

同一入口的玩家共享固定布局，鱼获分别进入自己的背包。复用现有邻近人物详细表现与远处简化逻辑；小场景分线容量通过密度测试确定。切后台、断线与返回继续遵循原有会话取消和命令恢复规则，保留已确认鱼获。

客户端两端可共用服务器地点目录，不依赖 iOS 尚未补齐的原生 POI 查询；iOS 的实际显示、进入与触摸仍需要独立验证。

新增地点与现有农场数据分开。服务端如调整领域/内容协议，实施显式兼容与迁移检查，保留账号、外观、装备、农场地形、作物及成熟时间、钱包、矿洞、历史命令和搬迁事实；应用版本沿用 0.16.x。

## 实施顺序与验收

1. **固定入口与三种灰盒。** 配置两城允许区域，用固定种子产生小批入口；同步制作图标、场景预览和对应灰盒，验证进入、1–2 屏构图与原位返回。
2. **完整钓鱼闭环。** 接入鱼塘在线空间，完成装备、选岸、抛竿、成功/失败、入包、双账号独立结算和恢复；检查三种轮廓的客户端/服务端一致性。
3. **目录稳定性与显示密度。** 验证并发生成、换设备、重启、跨缩放、城市边界与版本升级；按体验调整密度，既有入口不重排。
4. **美术与移动端验证。** 完成水面与岸边表现，在三种屏幕比例/分辨率检查触区、浮漂、镜头、后台恢复及连续进退资源释放。

关键验收：玩家从地图即可发现并进入鱼塘；入口名称、缩略图与实际场景一致；重进仍为相同位置和相同形状；三种轮廓清楚可辨且岸线可达；两个账号布局一致、鱼获独立；老账号与农场完整保留。真实水域资料覆盖率不作为本期的验收依赖。

本方案的本地实现与验收结果已经另行记录；本文中的候选参数不单独构成已验证或已发布结论。

## 附录：真实水域定位调研（本期不采用）

以下保留选型前的资料与抽样。关于真实水域的筛选和接入建议仅供后续研究，本期已选系统鱼塘，不执行这些接入步骤。

| Mapbox Streets v8 数据层 | 官方定义与可用性 | 建议用途 |
| --- | --- | --- |
| `poi_label` | `class` 包括 `park_like`、`sport_and_leisure` 等宽类别；这些类别本身不代表有水或可钓鱼 | 有明确钓鱼语义并通过水域核对的点可成为候选；公园、码头、游泳设施不能整类直接转换 |
| `natural_label` | `water` 对应湖泊、池塘；另有 `reservoir`、`river`、`canal`、`stream` 等；标签包含点和线等几何 | 优先发现有名湖塘和河段，取名称与水域类别；不是完整岸线，也不是现实经营信息 |
| `water` | 包含海洋、河湖、池塘、水库、喷泉等；按瓦片合并，没有可区分具体水体的 `class/type` | 辅助判断附近是否有水；不能用它直接分辨湖塘、喷泉或海洋，不能按每个面创建入口 |
| `waterway` | 线状 `river/canal/stream`；也包含 `stream_intermittent/drain/ditch` | 河段候选；排除排水渠、沟渠和间歇溪流等默认不合适类别 |

官方说明还指出，合并后的要素 ID 可能为 0，或取其中一个输入 ID。水体会随缩放过滤、简化、跨瓦片切分。因此，不能把 `water` 的 feature ID、局部面中心、屏幕中心或当前 zoom 当作永久入口身份。

原真实水域方案评估过的筛选过程：

1. 发现湖塘、河段候选，保留来源及原始语义。现有 OSM 农场地理模块可复用请求与部分解析，但它会将湿地等合并为水域，不能直接用其粗分类判断“可作为鱼塘”。
2. 使用可持久维护的水体资料建立游戏目录：首版可基于现有 OSM 接入或人工核对的自有地点配置。Mapbox 用于底图、运行时发现和显示；不把地图瓦片重组为游戏的永久水体主键。
3. 小湖塘默认一个主入口，大湖或长河只在有明确岸段区分时增加入口。用水体关联和空间距离去重，防止同一处水域同时通过 POI、标签、面、线生成四个点。
4. 已有 POI 原坐标保持不变；自建岸边入口有自己独立的经纬度。两个对象可以关联，但不能为避让图标把真实 POI 搬到岸边。
5. 泛化标签不足以排除喷泉、泳池、工业水池时，需要进一步资料或人工核对；未知状态不自动变成可用鱼塘。

原方案曾考虑以真实湖河名对应缩比例小场景。用户指出大水域与小鱼塘的空间预期不一致，因此本期排除该映射，不使用真实水域名称或轮廓承载系统鱼塘。

### Search Box 是否适合作为主来源

当前官方 Search Box 文档列出的支持地域为美国、加拿大和欧洲，未列中国大陆；其返回数据默认仅供临时使用，持久存储位置需要联系 Mapbox。因此不建议把 Search Box 作为同时覆盖洛杉矶、上海并永久保存入口的基础。它的请求计费也与现有 Maps SDK 瓦片读取不同。

Geocoding v6 已不再提供 POI，不能通过它的永久 geocoding 参数解决上述 POI 目录问题。这里的限制针对对应 API，不能直接套用为所有地图瓦片的存储条款；正式使用 Mapbox 派生持久数据时应核对实际产品授权。默认方案采用可维护的独立地点目录。
